To add a new detection method:
 1. Create a new class (like VarbitCompletionDetector)
 2. Inject EventBus and call eventBus.post(new TaskCompletionEvent(...))
 3. Register it in the plugin's startUp(), unregister in shutDown()
That's it. No other code changes needed.

Swappability Architecture

The TaskCompletionEvent is the contract boundary. The plugin subscribes to it and doesn't care who fires it:

[ChatMessageDetector] ──fires──→ TaskCompletionEvent ←──subscribes── [Plugin]
[VarbitDetector]      ──fires──→ TaskCompletionEvent ←──subscribes── [Plugin]  (future)
[WidgetDetector]      ──fires──→ TaskCompletionEvent ←──subscribes── [Plugin]  (future)

To swap out chat detection for something better: just write a new class that eventBus.post(new TaskCompletionEvent(...)) and register it. Zero changes to the plugin, store, resolver, or UI.

Key Takeaways from WikiSync for Us

• Manifest-driven everything: Server tells plugin what data to collect. New leagues = update manifest, zero plugin code changes.
• The varp IDs are REAL: 62 varps covering 1,984 task slots. These are the exact varps to monitor for Method 2 detection.
• Delta-only submission saves bandwidth: WikiSync only sends changed values. Our completion records are append-only (simpler), but task state could use this pattern.
• Quadratic backoff is clever: Retry on perfect squares (1, 4, 9, 16, 25...) — lighter than exponential, just as effective.
• `SyncButtonManager` is advanced UI: Injecting custom widgets into existing game interfaces. Cool for Phase 3.
• `stub_server.py` is genius: A 40-line Falcon server that mimics the real backend. We should do the same.
