We will need a database of some sort for our crowdsourcing (so that the data can be shared across the community). We'll need something similar to C:\Users\Strnger\Documents\Repos\examples\tog-crowdsourcing. We can start with a local database for testing. What tog-crowdsourcing does is:
When the plugin submits a finding, it sends a POST to /worldinfo with {world_number, stream_order}. The server first validates the payload and checks whether that IP has already submitted for that world by hashing ip + world_number and looking it up in IP_World_Blacklist. If not already present, it inserts that hash into IP_World_Blacklist. Then it looks in World_Information for an existing row with the same (world_number, stream_order). If one exists, it increments hits; otherwise it inserts a new row with hits = 1. (We won't need to blacklist, people will often play on multiple accounts, so each account could submit a task completion spot. HOWEVER, we should keep track of submission by IP. if there's a bad actor, we'll want to blacklist their IP and revoke all of their contributions)
So the persistent data is stored in a local SQLite file on the server named ./ToGWorldInformation.db. That file contains exactly two tables: World_Information(world_number, hits, stream_order) for the crowdsourced results, and IP_World_Blacklist(ip_world_hash) for one-submission-per-IP-per-world enforcement.
When the plugin wants the list, it sends a GET to /worldinfo. The server returns all rows from World_Information as JSON, and the plugin parses that response into an in-memory list for display. The client README explicitly says the web server is a separate repo.

For this exact architecture—one Linux Lightsail VM running Nginx + the Go API + SQLite, with Cloudflare in front—the likely cost is roughly $5–$24/month on AWS, plus $0/month on Cloudflare’s free plan, before domain registration. That range comes from current Lightsail Linux instance pricing: $5 for 0.5 GB RAM, $7 for 1 GB, $12 for 2 GB, and $24 for 4 GB. The repo’s README says the project uses a single AWS Lightsail instance, Nginx, and Cloudflare.
A realistic “cheap but comfortable” setup for something like this is probably $12/month or $24/month, not because the app is inherently expensive, but because a single Go API plus SQLite plus Nginx is lightweight and
 usually does not need much compute. If you want HTTPS termination and failover across multiple app servers using a Lightsail load balancer, add $18/month. Extra block storage is $0.10 per GB-month.
The first scale-up step is usually just bigger instance, same architecture. That means moving from $12 → $24 → $44 → $84/month on Lightsail as RAM/disk/transfer increase. For this project shape, that is the simplest and cheapest way to buy headroom.
The second scale-up step is multiple app instances behind a load balancer. For example, 2 × $12 instances + $18 load balancer = about $42/month, or 2 × $24 + $18 = about $66/month. That helps with availability and traffic spikes, but the current design’s real bottleneck is the SQLite database on one machine—once you have multiple app nodes, SQLite becomes the thing you most likely want to replace. That conclusion is an architectural inference based on the repo using SQLite on a single server and on Lightsail’s multi-instance/load-balancer model.
At that point, the normal move is to switch the database to a managed relational database. In Lightsail, managed databases start at $15/month standard or $30/month high availability; in Amazon RDS for PostgreSQL, pricing becomes more flexible but also more variable, based on instance-hours, storage, backups, and data transfer rather than one simple flat VM price.
Once you outgrow Lightsail entirely, AWS’s own guidance is that Lightsail load balancing is for low-volume traffic—they describe it as suitable for up to 5 GB and 400k connections per hour—and that services like ECS, EKS, App Runner, Elastic Beanstalk, Lambda, or EC2/ELB offer greater vertical and horizontal scaling.
